# 固定模块执行

## 已实现的范围

在侧边栏打开「Dify 回归工作台」，选择「按模块执行与记录」页签。这里支持将已人工批准的普通只读 API 套件绑定为不可变模块。每轮选择模块、运行方式、被测版本、数据标识和测试人；使用同一份固定请求与断言运行。模块名称、套件编号、内容指纹和环境版本保存在记录中。

发起方式有 `api-direct`（直接执行）与 `dify`（Dify 编排）。实际执行器均为 `api`。旧 API 记录也能在统一列表查看，未绑定模块的显示为「未归类 API 套件」。可按模块和发起方式筛选，下载原始 API 报告和查看实际证据。XMind 整理任务及手工回归仍在原页面，不作为自动执行记录。

## Dify 的执行原理

1. TestPilot 保存本轮任务，并检查模块和已批准套件指纹、测试凭据和本轮外部访问授权。
2. Dify `dispatch` 阶段接收匿名的运行编号、模块编号、指纹和固定 case ID 顺序。代码节点检查清单，输出固定动作 `execute-approved-suite`。
3. 本机核对返回清单必须逐项一致，然后调用现有 API 执行器。Dify 不能通过返回额外请求、修改 URL 或放宽断言改变执行。
4. 实际 API 结果和请求响应证据先存到本机，再向 Dify `report` 阶段发送匿名 case ID 与状态；Dify 统计真实结果数量。本机再次核对身份与计数。
5. 云端汇总故障单独标为流程异常，已保存的实际测试结果不会被修改。服务中断的运行标为阻塞，不自动重发请求。

Dify Cloud 无法访问本机 `127.0.0.1` 服务，因此采用上述本机桥接方式；不开放本机公网接口。工作流不包含 LLM，不会临时生成测试步骤。被测系统 URL、凭据、请求参数及响应正文不发往 Dify；只有匿名编号、指纹和状态在云端流转。

## 配置和日常操作

- 将 `integrations/dify/module-execution.yml` 导入 Dify，检查清单与输出节点后发布。其代码的来源是 `integrations/dify/module-execution.py`；修改后用 `node scripts/build-dify-module.mjs` 重建 DSL，再重新导入并发布。
- 在本机 `.env` 配置此应用专用的 `TESTPILOT_DIFY_EXECUTION_API_KEY`，可选配置 `TESTPILOT_DIFY_EXECUTION_WORKFLOW_URL`。与整理草稿的密钥分开。重启服务加载配置。
- 在现有 API 套件页面准备和审核固定用例，保留 `source` 与 `requirementRefs`。每个模块 1–20 条，每条最多 10 秒；当前不接入写请求、fixture、并发或角色矩阵。
- 到「按模块执行回归」绑定模块，核对来源、目标、预期和测试数据；填写审核人和意见。保存后模块不可编辑；修订需创建并审核新套件和新模块。
- 选择模块和发起方式，填写本轮环境信息，点击运行。外部目标还需明确勾选本轮授权。缺少 `${ENV:变量名}` 引用的凭据时，开始前记为阻塞。
- API 报告中的 HTTP 200 只是观测值；用例通过依赖完整固定断言。页面交互、颜色和复制动作需要单独的浏览器执行映射，不能用接口成功替代。

模块数据库位于 `${TESTPILOT_DATA_DIR}/module-regression/records.sqlite`，API 证据沿用 `${TESTPILOT_DATA_DIR}/api-runs/`。数据只在本机，不由 Git 同步。模块计划、直接 API 与 Dify 发起记录均可导出。

## 工具自测

`regression/shared/tool-selftest.api.json` 是内置 `/sample` 服务的完整样例契约，供验证工具机制。修改成当前本机端口后创建新套件、审核和绑定模块。它与部门申样书业务测试分开，不声称业务功能通过。

验证包括：固定断言成功和失败、Dify 清单被改动时不发请求、凭据缺失前置阻塞、Dify 汇总失败不覆盖实际失败、幂等请求、防止未批准套件接入，以及重启后记录保留。入口 `npm run test:dify`，运行前需要构建服务端；DSL 代码测试需要 Python 3，可设置 `TESTPILOT_TEST_PYTHON`。
