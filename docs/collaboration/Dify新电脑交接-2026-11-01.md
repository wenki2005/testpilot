## 新电脑恢复步骤（Windows PowerShell）

### 1. 获取源代码

安装 Git、项目兼容的 Node.js（`package.json` 当前要求 22.19+，依赖的 engine 约束以锁文件为准）、npm、Microsoft Edge。普通 `node`/`npm` 应在 PATH，不依赖旧电脑的 Codex 缓存绝对路径。

```powershell
git clone https://github.com/wenki2005/testpilot.git D:\Projects\testpilot
Set-Location D:\Projects\testpilot
git switch main
git pull --ff-only origin main
git status --short
npm ci
npm run build
```

克隆公开仓库通常无需登录；推送时使用具备协作者权限的 GitHub 账号。若依赖安装因 Node engine 不兼容失败，按安装输出升级兼容 Node，不用 `--force` 跳过约束。Edge 不在或明确要用 Chromium 时再安装 Playwright 浏览器：`npx playwright install chromium`。

### 2. 导入私有配置（在首次启动服务之前）

解压本次交接包，假设其位置为 `D:\Transfer\TestPilot-Dify-handoff`。先构建，再执行：

```powershell
node scripts/dify-machine-transfer.mjs import --input D:\Transfer\TestPilot-Dify-handoff\TestPilot-Dify-config.json --data-dir artifacts/demo
```

成功输出应包含 5 个模块、131 条最新用例、17 条最小用例，以及 `loginRequired: true`。导入不启动 Dify、不访问被测系统、不写目标数据库。新账号窗口标识重新生成，旧 Cookie 和认证状态不会带来。

若此前启动过新电脑服务，已经生成 catalog，工具会拒绝覆盖。先停止该服务，保留目录，改用一个**新的数据目录**，例如：

```powershell
node scripts/dify-machine-transfer.mjs import --input D:\Transfer\TestPilot-Dify-handoff\TestPilot-Dify-config.json --data-dir artifacts/demo-migrated
$env:TESTPILOT_DATA_DIR=(Join-Path (Get-Location) 'artifacts/demo-migrated')
```

后续每次启动保持同一 `TESTPILOT_DATA_DIR`。导入工具不合并/覆盖现有本机目录；两个电脑的 SQLite 文件不放网盘里同时读写。不带迁移包也可手动建系统、导入仓库五份 CSV、重新保存最小范围，但旧缓存与配置需重新建立。

### 3. 配置运行环境

复制 `.env.example` 为本机 `.env`，通过可信私有渠道取得所需值，本文件不含实际密钥：

```powershell
Copy-Item .env.example .env
```

必须确认：

- `TESTPILOT_DIFY_BASE_URL`：发布工作流的实际 API 地址；若旧电脑使用局域网/本机 Dify，新电脑需要能访问相应服务，不能机械使用新电脑 localhost 指向旧电脑。
- `TESTPILOT_DIFY_EXECUTION_API_KEY`：模块执行工作流密钥，固定回归必需。
- `TESTPILOT_DIFY_API_KEY`：用例整理工作流密钥，AI 辅助整理时需要。
- 两个可选的工作流编辑链接；企微通知地址仅在获授权测试群时另行配置：在 `.env` 设置 `TESTPILOT_DIFY_WECOM_WEBHOOK`（`https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=...`，仅限测试群），重启后还要在该系统设置里显式开启失败/截图通知。

同一个远程 Dify 工作流可以被两台电脑各自配置后调用，不因换编辑器必须重建。若要重新部署，工作流文件在 `integrations/dify`；导入、发布后新生成的密钥填本机 `.env`，不填进测试用例。

测试 MySQL 在当前工具中绑定专用测试源。新电脑在 TestPilot 的数据库工具中用授权用户名/密码重新连接；连接保存在进程内，重启后可能需要重新连接。数据目录包含本地固定书目及客户分类测试基线，超过 7 天会失效，需要按只读数据源刷新，不得把采集日期改新冒充重新取数。

## 两台电脑交替开发，怎样避免冲突

不同电脑本身不会破坏 GitHub；冲突通常来自同时改同一文件、没先更新、或强制覆盖远端。代码通过分支和 PR 汇合，本机状态各自保存。

**每次在另一台电脑开工前：**

```powershell
git status --short
git fetch origin
git switch main
git pull --ff-only origin main
git switch -c feat/dify-your-task
```

有未提交改动时先保护并检查它们，不能直接 reset/clean。分支名换成这次具体任务，已存在同名分支时先看远端/本地关系，不覆盖旧分支。两个电脑做不同工作使用不同分支，不同时向同一功能分支写入。

**下班或换电脑前：**

```powershell
git status --short
git add <本次确认要提交的文件>
git commit -m "说明本次实际改动"
git push -u origin <本次分支>
```

完成检查后开 PR，合并到 main，另一台再更新。若工作未完成，先推功能分支作备份，不为了换电脑把未经验证代码合到 main。Git 提示 non-fast-forward 时先 fetch、比较差异并解决冲突；不使用 `git push --force`、`git reset --hard` 或整目录覆盖来处理。

只本地 commit 没有 push，另一台看不到。Push 了功能分支但未 merge，另一台默认 main 仍看不到；可明确 checkout 该远端功能分支继续，或等 PR 合并后更新 main。

源代码变更不会自动同步两边系统配置、最小选择、截图、运行历史、密钥和目标数据库数据。需要同步模块配置时使用迁移工具导出并在新目录导入，不能把两个电脑的本机历史数据库互相覆盖。

## 接手开发的顺序与边界

1. 读 `AGENTS.md`、本交接和最新台账；查当前 Git 状态、分支、服务端口和数据目录；不重做旧计划初始问题。
2. 恢复配置、检查密钥、连接账号和只读库；确认系统/5模块/131条/17最小，先跑申请12条。
3. 若出现工具自身回归，先保留原轮证据，局部修复并定向验证；不把失败/阻塞改判通过，不删原断言。
4. 本人有可见记录后按用途/状态筛选→正向订单搜索→分页→详情与只读数据库对照逐渐扩展；只读找稳定数据，不造单、不借他人账号。
5. 目标 getInfo 字段、数量上限、后台入口/权限和通知渠道是具体业务/环境条件，明确缺项；没有条件时完成独立工作，不无限重复调用。
6. 只修改 Dify。涉及全局 UI、共享执行器默认行为、账号模型、全局调度或不确定其他入口影响的修改，先写文件/影响/风险/回退方案给用户判断。
7. 不修改目标业务系统，不提交/审批/取消申请，不写目标 MySQL，不泄露密钥/登录态，不把本地样例通过数算成部门申样通过。

本次发布、测试结果和 GitHub 合并记录以台账最后一节与 PR 为准。交接包和历史证据不是新的真实测试结论。
