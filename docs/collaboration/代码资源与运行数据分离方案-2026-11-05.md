## 一、交付目标

别人下载系统后，应当自带部门申样项目、全部用例、已有脚本、前置关系和核心链路，无需重新手工导入。历史运行批次、测试结果、截图、通知回执、个人账号配置和登录态不随包分发。

首次启动的正确状态是：项目可见、用例可见、脚本可编辑；运行报告为空，所有用例显示未执行，账号待连接。若用例需要真实审批、库存或下游服务，仍需相应环境和数据条件；不能承诺扫码后所有链路自然通过。

纪要中的两项重点分别落实：

1. 工具与用例管理：项目独立、逐条脚本文件、前置与核心链路、可视化编辑、在线报告、AI 编辑器通过 MCP 维护。
2. 工具分发与复用：资源完整、结果独立、配置本机化、首次启动自动装载、升级不覆盖本机记录、完整安装及 agent 接入说明。

## 三、目录边界：三类文件分别管理

以下均为目标结构，不是已迁移的目录。

### 1. 工具源码：TestPilot 仓库

```text
testpilot/
  src/                        工具服务、执行器、存储及接口
  web/src/                    界面
  scripts/                    启动、资源导入导出、构建、打包
  integrations/mcp/           MCP 配置模板和接入材料（计划）
  packaging/                  包体清单、平台启动器
  docs/                       开发、协作、分发与安装说明
  tests/                      工具自身测试
  package.json
  package-lock.json
```

工具源码继续通过现有 GitHub 版本管理。共享执行器及公共接口调整需兼容双方模块。不要借整理文件删除现有功能。

### 2. 业务项目资源：Codeup supply-sample-tests 仓库

```text
supply-sample-tests/
  README.md                   项目用途、运行及协作入口

  project-resources/

      project.json            项目稳定 ID、名称与目标环境模板
      modules.json            模块目录与顺序
      cases/
        orders-logistics/

      scripts/
```

这里存可以交接的业务定义，不存任务结果。按项目、业务模块组织；PC/H5 是客户端标记或子目录，不重复造两套相同用例。具体与李丰祺的模块归属单独明确，不能代为推定。

Codeup 项目资源与 GitHub 工具分别维护，通过工具版本引用和资源 manifest 组装交付；不要在两个仓库各放一份长期手改的相同工具代码。若团队要求单仓完整源码，应一次确定以哪个仓库为主，再建立镜像，避免双向人工覆盖。

Codeup 仅有资源时，README 必须明确依赖哪个工具版本，并提供获取/组装入口。下载源码仓库和下载可运行发行包是两种交付，不能把“资源仓库”描述成可直接双击运行的完整系统。

支持环境变量或配置选到其他磁盘；不要写死开发机的 D 盘或用户名。现有 runtime-data 暂时保留，通过受控迁移进入新布局；先备份、核对再切换，保留可回退路径。不要强行搬动正在被 SQLite 或浏览器使用的文件。

数据库物理拆分与目录调整分阶段完成：首阶段先实现干净资源导出/导入，不必立即重写全部执行器；后续再把本机定义库、结果库和凭据目录真正分离。发布排除靠允许清单和语义导出共同保证，不能只靠 .gitignore。

## 四、完整发行包应该包含什么

```text
TestPilot-Windows/
  app/                        编译服务与网页资源
  project-resources/          部门申样全部定义和脚本
  mcp/                        本模块 MCP 服务、配置及文档（实现后）
  config/                     无密钥模板、数据路径配置
  scripts/                    启动、初始化、资源升级入口
  docs/                       安装、运行、维护、故障处理
  runtime/                    明确选择的运行依赖策略
  启动TestPilot.cmd
  RELEASE.json                工具版本、资源版本、运行要求
  MANIFEST.sha256             包内文件清单及摘要
```

| 文件/内容 | Git | 完整分发包 | 本机数据区 |
| --- | --- | --- | --- |
| 工具源代码、配置模板 | 工具仓库 | 编译程序为必需；完整源码包可附源 | 无需 |
| 全部131用例、有效脚本、前置关系、4核心链路 | 资源仓库 | 必须带齐 | 首次启动装载并保存本机版本 |
| 缺步骤/待确认的用例及原因 | 资源仓库 | 必须保留 | 显示待补，不能假装可运行 |
| 浏览器执行所需的业务辅助脚本和模块配置 | 对应源码或资源仓库 | 必须随版本带齐 | 可缓存，不复制运行结果 |
| 运行批次、通过失败状态、运行时间、业务核验证据 | 不入库 | 不携带 | 保存 |
| 截图、日志、历史报告、通知回执 | 不入库 | 不携带 | 保存 |
| 报告名称备注/重要标记 | 不入库 | 不携带 | 跟随本人的运行记录 |
| 密码、Token、Dify Key、浏览器登录态 | 不入库 | 不携带 | 私有保存，按使用者配置 |
| 批准可共享的测试数据模板 | 资源仓库 | 携带 | 本机填写或选取 |
| 已提交申请号、真实订单、真实个人信息 | 不作为通用资源提交 | 不携带 | 留在历史证据/测试库 |

资源中不保留历史“通过”状态，只有定义和就绪性说明。必要的字段配置基线可作为定义保留，但不能把某次真实库存、审批进度和通知回执当作通用基线。

### 运行依赖必须说清

本地运行不代表零依赖。目前 Windows 启动器要求 Node.js，首次需安装依赖；浏览器、Dify、数据库及访问网络也有实际条件。建议分“开发源码版”和“Windows 完整运行包”：前者按文档安装，后者明确内置哪些运行依赖、哪些由环境提供、哪些首次联网下载。未打包相应运行时之前，不宣传离线解压即用。

## 五、用例文件、网页编辑、MCP 的统一源头

### 现阶段

现有模块数据库是当前有效源；regression/scripts 和 script-index 都是生成镜像，不能直接改文件后就算网页已更新。

### 计划的维护流程

1. 从当前真实模块版本导出完整项目资源：全131、有效缓存步骤、结构化前置关系、原文和来源、核心链路及版本映射；去除执行结果、凭据、机器路径和真实业务样本。
2. 逐条文件用稳定用例 ID 命名；模块目录可以变，ID 和关联不能依靠文件行号或 XMind 排序临时重编号。
3. 网页与 MCP 都调用同一套项目版本保存规则；每次修改同时维护用例、脚本和依赖，再导出候选资源文件。
4. 人工或 agent 改资源文件后走导入/校验，确认格式、ID、脚本协议、前置环和版本冲突，再加载成新模块版本。应用未实现导入/同步前，不把文件镜像标成可直接编辑。
5. Git 用于团队版本与合并；本机库是加载后的编辑/执行存储。保存资源版本和摘要，明确是否尚未导出或尚未导入；禁止运行时文件和库两边各自静默覆盖。
6. 新增、修改、停用分别处理；删除前查看依赖及核心引用。原用例和历史运行快照仍可追溯。

MCP 连接包需含 README、agent 指引、启动入口、编辑器配置模板和使用示例，并明确项目范围、当前版本、修改摘要。修改对比展示实际读回的变化；保存和执行分开，不自动提交业务申请，不重复要求确认用户已明确授权的同一修改。

## 六、首次启动与升级规则

### 新使用者

1. 运行启动器，检测依赖、端口和本机数据路径。
2. 在自己的数据区建立工作区，只导入资源定义。
3. 网页显示项目、全部用例、核心链路、脚本与前置关系；报告为空、用例未执行。
4. 填本机环境/Dify/数据库配置，登录本人测试账号；需要真实审批的步骤仍走对应人员流程。
5. 明确选择范围后执行，结果与截图写本机数据区。

### 已有使用者升级

- 分发包只读资源与本机数据路径分离，替换程序目录不影响报告和登录配置。
- 比较资源版本和摘要后新增模块版本，保留原运行关联；同版本重复初始化不重复造项目。
- 本机修改与新资源冲突时展示差异，用户选取后合并，不默认覆盖。
- 资源下架用例不删除旧批次的快照和截图；账号、运行记录和浏览器登录态不因升级清空。

| 5 | 改发行包与环境指引 | 完整系统包、接入包、依赖说明、启动器、摘要清单 |
