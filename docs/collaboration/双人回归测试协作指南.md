# 双人回归测试协作指南

适用对象：两名刚开始使用 Git 和自动化测试的实习生。日期：2026 年 10 月 22 日。

我们依据被测系统第一版人工测试的 XMind 用例，在系统更新后重复验证旧功能。两人按业务模块分工，各自完成用例理解、脚本实现和结果核对，使用同一个 Git 仓库协作，也可以让 Codex 协助实现。

本阶段不检查新增功能，不负责开发或修复被测系统。发现旧功能异常时，保留证据并反馈开发人员。需求文档用于解释业务预期；与 XMind 不一致时，记录疑问并请原测试人员或需求负责人确认。

## 一 我们如何分工

### 按业务模块负责完整工作

下列模块仅为示例，实际按 XMind 的一级或二级分支划分。任务开始前把 A、B 换成两人的姓名。

| 人员 | 示例模块 | 负责内容 |
| --- | --- | --- |
| A | 员工管理 | 整理原用例、准备数据、编写脚本、核对结果、补充模块说明 |
| B | 部门管理 | 整理原用例、准备数据、编写脚本、核对结果、补充模块说明 |
| 两人共同 | 公共能力 | 先做通一条样例，统一登录、配置、执行和报告格式，互相审核 |

每个任务尽量只包含一个小功能，例如“员工姓名查询的三条回归用例”。先完成并合并，再开始下一个任务。

### 公共文件一次由一个人修改

登录工具、数据库初始化工具、公共页面、统一执行入口、package.json 和 package-lock.json 容易被同时修改。需要改这些文件时先在任务记录中写明负责人，另一个人暂缓修改同一部分。公共能力合并后，双方同步再继续。

第一条样例由两人一起做：人工跑通一条原用例，再让自动化完成相同步骤，最后核对结果和失败证据。后续模块照这个样例实现，避免各写一套框架。

### 每天记录任务和交接

| 任务 | 负责人 | 分支 | 状态 | 涉及公共文件 |
| --- | --- | --- | --- | --- |
| 员工姓名查询 | A | test/employee-search | 进行中 | 无 |
| 部门名称查询 | B | test/department-search | 待开始 | shared/login |

交接时说明：做了哪些用例、怎么运行、哪些已验证、哪些尚未验证、是否需要对方先合并公共能力。模块负责人负责推进，对方负责复核，双方都要理解测试预期。

## 二 文件应该放在哪里

### 先共同维护现有项目

两人起步建议先共同维护一个 TestPilot 仓库，回归用例和脚本放进独立子目录。这样能一起修改现有工具，也能积累业务回归用例。后续规模扩大再考虑拆仓库。

当前代码目录是下面这个内层文件夹。初始化时进入这里，避免把外层报告和压缩包一起加入：

```text
D:\TestPilot-Demo-0.2.0-Windows\TestPilot-Demo-0.2.0-Windows
```

建议在现有结构上补充目录，保留原来的 src、web、tests 和 scripts，不为套用示例移动现有代码：

```text
TestPilot/                    # 共享 Git 仓库根目录
  src/                       # 现有工具代码
  web/                       # 现有界面
  tests/                     # 现有工具自身的测试
  regression/                # 建议新增的业务回归资产
    employee/                # A 的用例和脚本
    department/              # B 的用例和脚本
    shared/                  # 公共登录与数据工具
    fixtures/                # 脱敏样例与初始化脚本
  docs/regression/           # 用例依据、任务和精简测试结论
  .env.example               # 配置字段示例
  .gitignore
```

被测系统交付包、数据库备份另放在仓库外，按交付版本保存；已有来源仓库的代码按指定版本获取。需求和 XMind 可在允许的私有仓库中保存，或在文档中记录受控存放位置及版本。原始 XMind 留存不覆盖，改进用例另存并保留对应关系。

### 首次提交前配置忽略文件

在仓库根目录创建 .gitignore，已有文件则检查后补充：

```gitignore
node_modules/
dist/
.env
.env.*
!.env.example
artifacts/
runtime-data/
*.log
```

提交源码、package-lock.json、回归脚本、脱敏 fixtures 和精简结论。原始运行截图、录像、日志和数据库备份放在仓库外或被忽略的运行目录，结论中写证据位置。需要长期复用的已批准用例，应脱敏后导出到 regression，避免只留在 runtime-data 中。

.gitignore 不能移除已经提交的文件，也不能清除历史密钥。如果发现密钥已被提交，停止继续传播并先撤销或轮换密钥，再处理仓库记录。

## 三 首次配置 Git

### 两个人分别配置自己的电脑

从 Git 官方 Windows 安装页下载 Git，通常使用默认安装选项即可。安装后重新打开 PowerShell，逐条执行以下命令。示例姓名、邮箱必须换成自己的；它们用于标记提交作者，不是登录密码。[1][2]

```powershell
git --version
git config --global user.name '你的姓名'
git config --global user.email '你的邮箱'
git config --global --get user.name
git config --global --get user.email
```

统一使用公司允许的 Git 平台和私有仓库，每人使用自己的账号。首次推送或克隆时按平台要求完成浏览器登录、令牌或 SSH 认证，不把密码或令牌写进仓库地址。Git 是版本管理工具，Git 平台是两人共享代码的地方。

### 由一人建立共享仓库

如果已有原始仓库，直接沿用并确认写入权限，跳过初始化。确实没有仓库时，由 A 在平台创建空的私有仓库并邀请 B；不要勾选自动创建 README 或 .gitignore，避免与本地首个提交不一致。

A 在当前内层代码目录先建好上一页的 .gitignore，然后执行：

```powershell
cd 'D:\TestPilot-Demo-0.2.0-Windows\TestPilot-Demo-0.2.0-Windows'
git init
git branch -M main
git add .
git status
git diff --cached --stat
```

检查待提交文件，确认没有密钥、数据库备份和敏感测试数据。只有检查完成后才执行下列命令，仓库地址要替换成平台提供的实际地址：[3]

```powershell
git commit -m '初始化回归测试项目'
git remote add origin '实际共享仓库地址'
git push -u origin main
```

### 另一人克隆并启动

B 在自己电脑的工作目录执行。A 继续使用刚才的本地目录，不需要再次克隆：

```powershell
git clone '实际共享仓库地址' TestPilot
cd TestPilot
npm ci
npm run build
npm run demo
```

现有 README 要求 Node.js 22.19 或更高版本。两人尽量使用相同的 Node.js 版本。打开 http://127.0.0.1:4317 检查工具能否启动；这不代表被测系统也已启动。真实模型需要时各自配置本机环境，按现有 README 操作。

## 四 每个任务的 Git 操作

以下命令在本地 TestPilot 仓库根目录执行，示例任务为员工查询。先理解几个词：main 是共同主版本；branch 是任务分支；commit 是本机保存记录；push 是上传；pull 是取回并更新；PR 或 MR 是把任务分支合并进 main 的申请。

### 开始任务前同步并新建分支

先看 git status。存在未提交修改时，先在原任务分支整理、检查并提交，或按下一页方法临时保存；不要直接切换任务。

```powershell
git status
git switch main
git pull --ff-only
git switch -c test/employee-search
```

一个小任务一个分支。B 可使用 test/department-search。main 平时用于同步和验证，日常改动在任务分支进行。

### 修改后检查并上传

让 Codex 完成指定任务后，人工核对原用例并运行相关检查。git diff 显示未暂存的已跟踪文件差异，新文件要另外打开查看；git status 会列出新文件。

```powershell
git status
git diff
git add .
git diff --cached --stat
git diff --cached
git commit -m '增加员工姓名查询回归用例'
git push -u origin test/employee-search
```

git diff --cached 显示本次准备提交的内容。确认没有无关修改和敏感数据。后续在同一任务分支继续工作，重复检查、add 和 commit 后，执行 git push 即可。commit 只存在本机，push 后对方才取得到。

### 在平台申请合并并互相检查

上传分支后，在仓库网页创建 PR 或 MR，来源选择任务分支，目标选择 main。说明对应哪些 XMind 用例、如何运行、验证结果以及未验证项。对方需要实际运行时，可在工作区干净的前提下执行：

```powershell
git fetch origin
git switch --track origin/test/employee-search
```

这只用于第一次建立该分支的本地副本；已经有同名分支时，改用 git switch test/employee-search，然后 git pull --ff-only。审核人确认用例预期和执行结果，给出意见；作者修正并推送后，网页中的同一合并请求会更新。

审核通过后在平台合并到 main。两人下次开始工作前都执行 git switch main 和 git pull --ff-only，再为新任务建新分支。已经合并的旧任务分支不再用于新增任务。

## 五 同步公共修改和处理冲突

### 正在做的任务如何接收最新 main

另一人的公共登录或配置已合并，但自己的任务还没完成时，先把当前修改检查并提交，使工作区干净。确认当前仍在自己的任务分支，再执行：

```powershell
git branch --show-current
git status
git fetch origin
git merge --no-edit origin/main
```

没有冲突时，运行相关验证后 git push。如果这是分支第一次上传，使用 git push -u origin 当前分支名。更改依赖后按锁文件运行 npm ci。同步主分支和提交代码是不同动作，使用 Codex 前也要确认当前分支是否需要同步。

### 遇到冲突时如何处理

冲突表示两边改动需要人工选择或组合。先运行 git status，查看哪些文件冲突；让 Codex 对比双方意图，提出保留方案，再确认实际修改。文本冲突常包含 <<<<<<<、======= 和 >>>>>>> 标记。

解决每个冲突后，检查代码并运行相关验证，再执行：

```powershell
git add .
git diff --cached
git commit -m '合并主分支并解决冲突'
git push
```

如要取消刚才的合并，在合并尚未完成时执行 git merge --abort，返回合并前状态。开始合并前提交本机修改，能降低恢复困难。[4]

不要用“全部接受我的”或“全部接受对方的”草率处理。XMind、Word 等文件通常不适合逐行合并，约定同一时间一个人编辑；依赖文件冲突需要确认实际依赖，再生成一致的锁文件。

### 新手常见情况

| 情况 | 建议处理 |
| --- | --- |
| 提示不是 Git 仓库 | 检查是否进入内层代码目录，用 git status 确认 |
| 本地修改阻止切换分支 | 先提交；暂不提交可用 git stash push -u，切回后 git stash pop |
| 推送被拒绝 | 检查权限、分支和远端变化，让 Codex 解释原始报错，不使用强制推送 |
| pull --ff-only 失败 | 可能有分支分叉，保留现场检查，不反复执行或重置 main |
| LF 和 CRLF 警告 | 先确认是否只是换行提示，避免为了消除提示全量改写文件 |

stash 是本机临时保存，不会上传；pop 也可能冲突。两人初期不使用强制推送、硬重置或清理未跟踪文件来解决一般问题。已合并的错误优先用纠正提交修复，必要时请 Codex解释如何安全撤销。

## 六 如何让 Codex 协助

### 各自打开各自克隆的项目

两人分别在自己的电脑打开本地仓库，在自己的任务分支上使用 Codex。给出目标、相关资料、限制和完成标准，让它读取当前结构并运行相应检查。完成后查看差异并核对结果；代码生成成功不等于业务用例验证通过。[5]

Codex 是否能解析 XMind 取决于实际文件和可用工具。无法读取时，导出为文本或 Markdown，并保留用例编号和分支路径。不要让它凭名称猜测业务规则。

### 实现任务时复制这段提示词

```text
我们依据第一版 XMind 做旧功能回归，不测试新功能。
请先检查当前分支、工作区和项目现有结构。
本次只做员工查询模块，对应 XMind 编号 EMP-001 至 EMP-003。
请读取我指定的 XMind 或导出文本及相关需求。
沿用已存在的执行、登录和报告机制，不另建一套框架。
原用例缺少步骤、数据或预期时，请列出问题，不自行编造。
请实现可重复运行的脚本，明确数据准备和清理方式。
只改本模块；需要改公共文件时先说明原因和影响。
完成后运行相关检查，列出修改、执行命令和真实验证结果。
环境不具备时明确写未验证，不用模拟结果宣称已通过。
先不要提交、推送，也不要修改被测系统来让测试通过。
```

模块、编号和资料位置要换成实际内容。先让 Codex 完成一个小任务，审核后再扩展。

### 看不懂代码时让它解释

```text
请对照原 XMind，解释本次每条脚本在测什么、检查了什么。
指出哪些地方只是页面操作，哪些地方真正判断业务结果。
请检查是否存在只等待页面打开就算通过、忽略错误、
降低预期或硬编码成功结果的问题，并说明验证限制。
```

### 两人统一给 Codex 的项目规则

可共同编写仓库根目录的 AGENTS.md，写清目录、运行命令、模块分工、预期依据、不得提交密钥和结果核验要求。[5] 文件中的规则由两人共同确认，示例原则为：

- 用例保留 XMind 编号或路径；需求不清时记录待确认项。
- 不修改被测系统，不通过删断言、跳过错误来制造通过结果。
- 公共文件改动说明影响；验证报告区分实际执行与尚未执行。
- 提交和推送按当前任务明确指令执行；不覆盖对方未提交修改。

本指南中的“先不提交推送”是两人的初期协作约定，不是 Codex 的产品限制。确认后可以明确让 Codex 帮忙提交到指定任务分支。

## 七 每次回归具体怎么做

### 先补齐原用例的执行条件

示例用例 EMP-001，来源路径为“员工管理／员工查询／按完整姓名查询”。这是格式示例，实际预期以原 XMind 和确认后的需求为准。

| 字段 | 示例内容 |
| --- | --- |
| 准备条件 | 使用独立测试账号，存在测试员工 REG_A_001 |
| 操作步骤 | 登录，打开员工列表，输入 REG_A_001，点击查询 |
| 预期结果 | 列表显示该员工，姓名等指定字段与准备数据一致 |
| 数据处理 | 重跑前确认样例存在；仅清理本用例创建的数据 |
| 对应脚本 | regression/employee 下实际保存的脚本路径 |

先人工执行并确认预期，再实现自动化。某些用例不能稳定自动化时，保留人工执行步骤和结果，不把“未自动化”写成“通过”。

### 被测系统更新后的操作顺序

1. 记录本次被测系统交付版本、XMind 版本、测试环境和测试代码提交号。提交号用 git rev-parse HEAD 获取；有本地未提交修改时应说明，正式记录优先使用已提交版本。
2. 启动或连接被测系统，检查账号、权限、接口和数据库可用。只有前端与数据库时，先确认后端服务由谁提供。工具启动成功并不表示这些条件已满足。
3. 准备约定的脱敏测试数据。各自本地数据库最好独立；共用环境时用 A、B 不同的数据标识，协调有删除或清空行为的用例。禁止对共用库执行全库清空来重置测试。
4. 选择旧用例执行，保存当次结果、实际输出和失败截图。每个模块写清自己的运行方法，能由另一人在相同条件下重跑。
5. 分析异常并反馈。系统缺陷交给开发处理；数据或环境问题修正条件后重跑；需求变化先确认依据，再更新预期并保留变更记录。

### 结果状态要表达清楚

| 状态 | 含义 |
| --- | --- |
| 通过 | 已执行所需步骤，实际结果满足明确的预期 |
| 失败 | 已执行，但实际结果不满足预期，尚需分析原因 |
| 阻塞 | 账号、环境或条件缺失，无法完成执行 |
| 待确认 | 原用例或业务预期不明确，需要相关人员确认 |
| 未执行 | 本轮尚未运行，不能算通过 |

失败记录至少包含：用例编号、系统版本、环境、准备数据、操作步骤、预期、实际结果、截图或日志位置，以及能否重现。测试失败与已确认系统缺陷分开记录。开发修复后，使用相同预期复测，并保留前后记录。

## 八 两人从哪里开始

### 第一次协作的安排

1. 共同确认被测环境能运行、交付版本明确、XMind 能打开，列出缺少的账号、后端地址和测试数据。
2. 按实际业务模块划分负责人，每人先选三到五条旧用例。共同确认编号、步骤、预期及公共文件负责人。
3. 按本指南建立或沿用共享仓库，两人都完成本地启动；共同做通一条样例并合并 main。
4. 各自新建任务分支，让 Codex 协助完成一个小功能，互相审核和重跑，再合并。
5. 在被测系统下一次交付时，按第七部分完整重跑一次，检查结果是否能追溯到用例和版本。

第一阶段完成标准：双方都能取得同一版本代码，依据原 XMind 重复执行各自模块用例，另一人能复现结果，失败时能看懂原因和证据。自动解析全部 XMind 或增加复杂 AI 能力，等这一流程稳定后再考虑。

### 提交合并请求时填写

```text
任务和模块：
对应 XMind 编号或路径：
修改内容：
被测环境及所需测试数据：
执行命令或人工操作：
实际验证结果：
尚未验证及阻塞原因：
公共文件与影响：
```

### 每天可对照的简短流程

开始：确认工作区干净 → 切到 main → 拉取更新 → 新建任务分支。

开发：对照原 XMind → 在本模块修改 → 运行验证 → 查看差异。

提交：add → 查看暂存内容 → commit → push → 发起合并请求。

合并：对方核对预期与运行结果 → 修正意见 → 合并 main → 双方同步。

当天没有完成时，可将已检查的阶段性工作提交并推送到任务分支，但不合并 main；第二天切回同一任务分支继续，不再创建同名分支。
