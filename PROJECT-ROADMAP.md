# TestPilot roadmap and implementation record

Updated 2026-10-16.

## Product center

The core product is a persistent, reusable test-script lifecycle:

1. Create or import a candidate test script from requirements and observed project behavior.
2. Review the script and its changes; a human approves a specific immutable version.
3. Run that approved version manually or in CI with a deterministic runner and no model dependency.
4. When the application changes, use AI or a human to propose a script update, review/version it, then run the full approved regression set.

Bounded autonomous exploration is a supplementary source of reviewable test candidates. It does not replace executable approved scripts.

## Completed: imported script lifecycle MVP

- The registered `grammar-lab` profile imports its existing suite definition and an explicit source allowlist: `package.json`, `tests/model.cjs`, and `tests/browser.cjs`.
- Candidate snapshots include the full suite and source file contents. A SHA-256 digest covers profile ID, suite, and source files. The workbench displays the captured sources and a concise diff against the latest approved version (case additions/removals/order and command/expectation changes, plus changed source paths).
- A reviewer can approve or reject a candidate with notes. Approval persists an immutable version. Only approved versions can run through the lifecycle endpoint.
- Approved runs use the existing `DeterministicEngine` and no-shell command runner. They overlay the approved source snapshot onto a disposable project copy and record the approved script ID, version, and digest in normalized JSON/Markdown evidence.
- Source file paths are profile-controlled, project-relative allowlist entries. Candidate capture checks regular files and canonical containment; execution rejects traversal and links and writes only into the temporary copy. The configured D:/work project is never written by this workflow.
- Persistent script versions and run records survive demo server restarts. The UI exposes candidate/review/approval, command/file diff, approved rerun, status/output, report links, and retained target artifacts.
- This is a manual/imported candidate. It is not an AI-authored script, and it does not infer tests from requirements. The separate API Agent demo can produce transient model-proposed checks, but those are not stored as executable scripts and are not silently promoted.

## Completed: requirement-driven authoring MVP (Grammar Lab only)

- The workbench accepts one feature requirement for the registered Grammar Lab profile and uses the existing Pi Agent Core / Pi AI OpenAI-compatible provider configuration.
- The model can submit exactly one candidate through a single tool. Its output is constrained to a 1–12-step declarative DSL: click, exact/contains text assertion, visibility assertion, or disabled assertion.
- TestPilot validates every operation and selector against a fixed Grammar Lab allowlist, then emits a TestPilot-owned Playwright runner and JSON manifest. The model cannot write arbitrary JavaScript, run shell commands, choose files, or trigger execution. The package test hook, manifest, runner, suite, and source allowlist are persisted only in the TestPilot candidate store.
- The resulting candidate keeps the original requirement, proposed test title/summary/steps and source snapshot. Review and approval are still required before any project copy executes. The approved package/test snapshot runs through Grammar Lab's existing Playwright dependency from a disposable copy with no model configuration.
- Verification uses a local OpenAI-compatible SSE mock endpoint through the real Pi adapter, then reviews/approves the candidate and runs the snapshot with model configuration removed. This proves protocol integration and deterministic execution, not real model authoring quality.

## Current boundaries

- AI requirement authoring is a narrow Grammar Lab MVP, not a general app author. It uses known UI facts and a small safe DSL; it does not inspect arbitrary DOM, generate general Playwright code, author target files directly, or heal failing tests.
- Diffing is concise and path/case-level; it does not yet provide line-level source diffs, rich review comments, or safe in-product source editing.
- The explicit profile allowlist contains Grammar Lab, Plural Runner, Book Companion, and Word Runner. AI requirement authoring and immutable candidate review remain limited to Grammar Lab; the other profiles run only their fixed existing suites.
- Each profile command is normalized as a process case. Framework-level individual assertions are still represented in stdout and retained target artifacts, not parsed into TestPilot's per-assertion evidence model.
- Current profile execution is a local allowlisted runner, not a hardened multi-tenant worker sandbox. CI orchestration, team roles, remote agents, and production environments are not implemented.
- The API Agent workbench remains a separate demonstration of bounded API exploration. Its protocol fixture verifies integration behavior, not live model quality or approved script lifecycle.

## Next phases

1. **Broaden requirement authoring:** provide more project context, support additional safe DSL operations and target profiles, retain traceability from requirement to assertions, and measure outputs against human-reviewed requirements.
2. **Safe script maintenance:** when application behavior or source changes, ask AI or a human to update tests in a disposable workspace; produce line-level source diffs, validate scope, run checks, and require approval before saving a new immutable version.
3. **CI/manual runner interface:** expose stable version selection and run metadata for CI; guarantee the execution path has no model dependency and records the exact version/digest and environment boundaries.
4. **Normalized runner evidence:** reuse native Playwright Test / Node test reporters to capture individual tests, retries, traces, and attachments without replacing their browser drivers.
5. **Bounded autonomous candidate discovery:** let planner/generator/healer helpers explore within file, action, and time limits. Treat outputs as separate reviewable candidates; do not conflate exploratory checks with the requirement-linked saved suite.
6. **Application matrix expansion:** use the isolated local profiles for Book Companion and Word Runner, then add other web/API/mobile/desktop types only with their own fixed fixtures and run evidence. Maintain per-project evidence and never infer cross-app coverage from one target.

Use Playwright Test Agents as an architectural reference: agent helpers work around normal executable Playwright tests. Do not copy substantial OSS source; reuse supported packages and each target's existing test runner under its license. Each phase must preserve the distinction between candidate generation, human approval, and deterministic execution.

## HTTP API adapter first slice (2026-10-16 continuation)

- Added an independent, deterministic `run-api` CLI suite format alongside the existing command runner. Cases assert response status, selected headers, recursive JSON subsets, and maximum duration; evidence and run history use the existing normalized JSON/Markdown reporter.
- Requests are confined to the configured target origin and path prefix; redirects are not followed; responses are capped at 1 MB; environment-backed credentials are scrubbed from request/response evidence. Non-loopback hosts require `--allow-network`; POST/PUT/PATCH/DELETE require `--allow-mutations`.
- Each API case may declare a bounded concurrent request batch (maximum 50); concurrency is blocked unless `--allow-concurrency` is explicit. Total run evidence is capped at 5 MB. Mixed batches preserve a failed check as run-level failed even if another check is blocked.
- Cases can declare an access-control matrix over named principals. Each identity must have its own expected status/result, and credential headers are required to use `${ENV:NAME}` references; local evidence redacts credential values. This supports endpoint role checks but not interactive login/session acquisition or application-specific authorization discovery.
- Suites can declare explicit fixture setup/cleanup HTTP cases and interpolate the unique `${RUN_ID}` into paths, headers, and JSON values. Every mutating test/setup call requires cleanup that references the same run ID. Setup failure blocks business checks; cleanup runs in reverse order even after assertion failures or cancellation, and cleanup failures affect the run outcome. This is a user-authored isolation contract: the runner does not prove that cleanup removes every side effect.
- Local HTTP fixture verifies the actual CLI entry point, auth header injection/redaction, contract mismatch vs transport/timeout results, redirect isolation, path-prefix escape, and that mutations/concurrency do not reach the target until explicit opt-in. The concurrency fixture observes simultaneous overlap on its local server.
- This starts Stage 3 but is not a full API test platform. It has no generated OpenAPI suites, interactive auth/session acquisition, app-specific authorization discovery, sustained load metrics, DB migration validation, or integration into the document-driven UI/MCP approval flow. Fixture setup/cleanup and role expectations are user-authored and must be run against a dedicated test environment.

## API test authoring in the main workbench (2026-10-16 continuation)

TestPilot then creates a bounded index of paths, methods, parameters, request/response schema details, response status codes, and security schemes, and checks generated references, methods, executable paths, and expected statuses against that index. It resolves in-document JSON Pointer refs, rejects remote/unresolved refs and recursive non-schema refs, and preserves a marker at recursive schema edges. The generated suite records operation keys and cited/uncovered operations; draft edits recalculate this against the stored contract baseline and reports/UI show the count. It rejects malformed YAML, schema-invalid documents, unsupported Swagger 2.0, unknown operations, path mismatches, and undocumented statuses. Schema validation does not prove operation behavior or semantic test adequacy; enum combinations, negative/auth/boundary adequacy scoring, and exhaustive coverage remain unimplemented. An isolated headless Edge UI fixture covers selecting API mode, submitting requirements/OpenAPI text, model-backed candidate generation through a local compatible endpoint, the automatic read-only gate, the API request, and result/report-package availability. The UI also lists persisted API suites; reopening a saved candidate restores its state without silently rerunning the request, covered by the same fixture. The fixture disables public web search and uses only a local API target; real provider generation quality and online-search behavior remain unverified. Next: measure negative/auth/boundary adequacy with fixtures before beginning app-specific auth discovery, database migrations, or sustained load/latency testing.

## Generic SQLite migration CLI first slice (2026-10-16 continuation)

- Added `run-migrations --suite ... [--project-root ...]`, a declarative suite loader and a restricted SQLite runner using Node's built-in `node:sqlite`.
- Each scenario gets a new in-memory database. Baseline, fixture and migration SQL files must resolve inside the selected project root, be regular files without symlinks, and stay within 512 KB per file / 5 MB total sources. Assertions accept a single `SELECT`, compare exact rows, and cap results at 500 rows.
- SQL scripts accept CREATE TABLE/INDEX, ALTER/DROP TABLE/INDEX and INSERT/UPDATE/DELETE. `ATTACH`, `DETACH`, `VACUUM`, PRAGMA, transaction-control statements, virtual tables and extension loading are excluded. Each migration runs under a savepoint. A scenario can expect its final migration to fail and assert the state after savepoint rollback.
- Scenarios run in separate Node child processes with `--max-old-space-size=128` and an 8-second hard timeout; the parent sends SIGKILL when exceeded and records `blocked`. This is necessary because a synchronous SQLite query in a Worker thread did not reliably stop when `Worker.terminate()` was requested. Refusal, rollback and high-cost query fixtures cover those paths.
- JSON/Markdown run records and a ZIP containing the suite, SQL source snapshots and evidence are written. The example CLI passes in both `tsx` development and built `dist` execution. Node 22 currently emits an ExperimentalWarning for `node:sqlite`.
- Normalized run JSON includes the SHA-256 of the exact suite + SQL snapshot, SQLite runtime version, ordered migration events, expected rollback details and per-check expected/actual rows. Markdown renders those fields instead of requiring consumers to parse a combined stdout string; the ZIP contains the same report and JSON evidence.
- Boundary at the CLI increment: SQLite only; no file-backed DB, arbitrary migration runner, database server, PostgreSQL/MySQL, or production target. Use synthetic fixture data; SQL sources and expected rows are included in the downloadable package.
