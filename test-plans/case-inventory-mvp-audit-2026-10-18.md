- 项目当前 156 条中 **35 条已有步骤，121 条空步骤**。全量运行并没有覆盖全部：确定性 8 passed / 9 failed / 139 blocked；Computer Use 3 passed / 7 failed / 146 blocked。该 run 是修复前的基准。

## 已有真实证据及准确步骤

### case-81：可直接重放、已双通道验证

目标站运行证据：`execution.json` 中 `case-81` deterministic/computer-use 均为 `passed`；Computer Use 明确观察到订单物流页及所有状态计数为 0，并看到精确空态“暂无订单物流记录”。项目现有 DSL：

```json
[
  {"action":"clickExactText","text":"订单物流"},
  {"action":"assertExactVisible","text":"暂无订单物流记录"}
]
```

适用范围：当前登录账号确实是受控空订单账号。该步骤证明当前账号的空态显示，不证明其它账号/状态筛选或订单内容。

### case-83：脚本可重放，但现证据不支持“搜索无匹配”结论

目标站记录观察到搜索框 placeholder 为“搜索订单号/书籍”，并在查询后出现空态。但查询前计数就是全部 0；当前脚本没有先证明列表有记录，也没有结果差异可以归因于关键词。因此虽然两 lane 形式上 passed，语义仍未验证。

要验证完整 case-83 的最小可靠方案（**待 fixture，不能直接对生产现有账号执行**）：准备至少 1 条属于测试账号、可只读查看的订单，确认搜索前结果数为 1+；使用不可能匹配的唯一字符串搜索，再断言结果数变为 0/精确空态。当前 DSL 还缺集合计数断言；若仅用视觉行文本，需新增稳定的列表结果计数能力。不要靠 Enter/回车是否触发接口的猜测做通过判定。

## 对现有结果的复核与建议

1. **保留真正观察到的失败**：case-10、26、31、42、45、49、94 的全量记录中有目标页实际视觉结果及失败条件，是当前可用的缺陷复现与回归条目。应修产品或请需求方决定冲突文案，不要把 expected 改成页面现状来“消除”失败。
2. **修复 case-83 的结果语义**：需测试引擎支持 precondition/fixture evidence，并对“查询前非空、查询后零项”同时断言；若没有数据夹具，应报 blocked/incomplete。旧结果的 `passed` 是过度结论。
3. **区分 N/A、澄清、blocked、partial**：N/A 不应当排队后变 blocked，也不可算通过；澄清项保持待确认；部分 UI 子步骤不能抹掉完整用例的 gap。
4. **不要批量改写风险为 none**：风险、账户、角色、数据夹具和业务副作用分别建门禁；不确定时 fail closed，但页面只读检查可以作为不解除 gap 的部分证据。
5. **最小下一步**：若要继续填真实 UI 脚本，需要在当前持续登录的 TestPilot 浏览器内只读进入“历史申请记录”和“订单物流”，保存 DOM/截图证据（包括 URL、菜单文案、实际列头）；然后选 80/87/88/89/90 中仅有标签可见性部分补步骤，并标注 coverageGap。case-82/83/89/90 的完整功能验证应先准备测试数据，而不是继续在当前空数据账号上猜测。
