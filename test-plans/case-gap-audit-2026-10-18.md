## 范围与证据

- 权威用例：`artifacts/demo/document-tests/projects/624a5e81-e79e-493f-a746-8accc5c44b90.json`，156/156 全选。
- 最终全量证据：`artifacts/demo/document-tests/runs/3d85d43e-7248-4e44-a9a5-eaa6d02cc1d7/run.json`、`execution.json`、`report.md`；初始逐项审计记录仍可在 `71a60764-c2aa-4004-9344-84b3e28aa165` 中查阅。
- 最终基准运行确实提交 156 条，但并不等于 156 条均完成测试：确定性 8 passed / 9 failed / 139 blocked；Computer Use 3 passed / 7 failed / 146 blocked；`finalReady=false`、`overall=unresolved`。
- 当前项目有 35 条非空步骤、121 条无步骤；此前审计将 8 条识别为完整只读步骤，其余步骤有不同程度的 coverageGap。非空不代表有效：每条仍须核对路由、定位器和验收点。

## 结论

“没有步骤”不能简单归咎于安全门禁。根因分三种：

1. **确实需要后端/受控业务数据**：API 权限、审批、库存锁定、订单持久化、第三方回调、消息投递、迁移一致性、并发、OAuth/token 等，浏览器上加几个页面断言无法证明期望。
2. **可以先补安全的页面子步骤，但完整用例仍应 blocked**：订单/历史申请列表和详情、筛选控件/字段标签、PC 管理界面可见入口、状态标签。这些步骤有助于定位页面/验证 UI 存在性，但没有合适记录夹具或分页/过滤/值断言时，不能据此报完整通过。
3. **应明确保留为澄清或 N/A**：源用例本身是待澄清或明确不在本期范围。写入通用页面步骤会掩盖需求缺失。

原始零步骤用例中有 **17 条候选**曾建议补“安全但明确不完整”的 UI 子步骤（下表）；这是待页面证据确认的候选，不是可直接导入的脚本。独立复核后确认，现有记录没有更多候选同时满足“真实目标页证据、无额外角色/fixture、无副作用”；case-81/83 已补入并两通道验证通过。其他候选须先取得真实 DOM/可见页面证据，且可保留 `coverageGap` 让结果保持 blocked。

当前全量项目中的 121 条空步骤分布为：55 条 `irreversible`、61 条 `unknown`、5 条 `none`。这 5 条无副作用标记的用例都带有范围外或 PC 后台/角色等 `coverageGap`，因此在最新 fail-closed 规则下，**目前 0 条空步骤用例满足自主探索准入**。这不是忽略用例：需要先把范围外项标成 N/A、为 PC 项提供对应授权页面/角色，并对需要夹具的情况建立隔离数据，再补可验证脚本。不得仅将风险改成 `none` 来绕过缺口。

## 推荐补的只读 UI 子步骤

先在现有 TestPilot 管理浏览器里进入对应页面，确认 selector/文案真实存在，再加入这些受 `coverageGap` 约束的草案。不得点击提交、审批、删除、锁单或消息发送。

### 可执行 DSL 形状（仅候选模板，定位器经 DOM 确认后才能落入项目）

```json
[
  {"action":"clickExactText","text":"订单物流"},
  {"action":"assertVisible","text":"订单号"},
  {"action":"assertVisible","text":"订单状态"}
]
```

模板最后一行不可预先当真：只能对目标页面实际出现且语义匹配的列头断言。每个补出的用例都要写精确 `coverageGap`，例如“只证明列表列头存在；数据值与20条分页未验证”，这样两个 lane 必须保持 `blocked` 而不是 partial passed 被包装为通过。

## 后续全量复跑暴露的执行器根因

最终基准运行 `3d85d43e-7248-4e44-a9a5-eaa6d02cc1d7` 显示脚本侧 139/156、Computer Use 侧 146/156 blocked。复核 `runComputerUseLane` 后发现：Computer Use 在调用视觉模型前硬性要求 `item.steps.length > 0`，因此所有空步骤用例都没有获得自主探索机会。这是执行器缺陷，不能归因为 121 条都缺 UI 路径。现已修改视觉通道：符合准入条件的空步骤用例可从截图自主探索；明确依赖账号、业务 fixture、澄清、范围外、未知副作用风险或未解决 coverage gap 的事项仍 blocked，且危险动作仍被浏览器门禁拦截。改动通过最新 59 项 demo 回归，但暂未在目标站全量重跑。

## 当前分类及产品修复建议

1. **先把 `blocked` 与 `N/A` 分开**：明确范围外的 16、71、72、95 应有 N/A/排除状态；待澄清要 `needs-clarification`，而非普通 blocked。保留 156 条源节点追踪，不把 N/A 算通过。
2. **生成安全的 UI 子计划**：case 80–93、132/133、136、154/155 有少量只读页面可见性/表单子断言；路由和定位器验证后补进脚本，同时保留 incomplete coverage。不要把 17 个建议都盲目导入，先对目标 app 当前页面做 locator evidence。
3. **为完整测试补 API lane，不编造 endpoint**：拿到 OpenAPI/契约、隔离 sandbox、身份和数据 cleanup 策略后，把纯负向请求、列表只读检查、配置读取纳入 approved API suite；涉及 mutation 时用 synthetic per-run fixture 与清理回滚。生产写接口禁用。
4. **让 UI DSL 补齐真实缺口**：集合计数/按行行数断言、URL/path 断言、clipboard read、`select` 选项/值、计算样式，以及安全地监听网络请求。`assertFieldInvalid` 不足以代替隐藏字段状态或消息是否已发送。
5. **结果对齐需落到每条 assertion**：Computer Use 提示中要求回报 exact locator/value/evidence；两 lane 比较同一个期望、当前仅截图或泛化标题的结果不得算 aligned。存截图/DOM 证据引用，不把失败 lane 的定位器错误算目标缺陷。
6. **全量状态如实展示**：这次是 156 条均入队、并非 156 条均实际验证。报告应分列 completed/pass/fail/blocked/N/A/clarification 和覆盖百分比；`finalReady=false`，不是通过可交付基线。
