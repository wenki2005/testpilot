# 部门申样书 156 条用例：阻塞根因与修复记录（2026-10-18）

## 为什么上次看起来“有状态却没有执行”

Run `074bc5be-1ad8-4ef8-82b3-64493584b269` 把 156 条全部纳入范围，但这只代表每条拿到了运行状态，不代表每条都运行了有效断言。该轮确定性通道为 9 pass、6 fail、141 blocked；Computer Use 为 7 pass、6 fail、143 blocked。141 条 blocked 不是 141 个产品缺陷。

阻塞数的构成是：76 条风险标签为 `unknown`、60 条为 `irreversible`、另有 5 条具体前置条件没有确认。用例步骤生成器此前只允许 `sideEffectRisk=none`、预期已确认的用例开始生成；而导入器又给大量无关用例写入同一条未确认前置条件“需要目标系统专用测试环境和/或测试账号、接口 mock/沙箱数据”。因此，即使某条实际只需检查字段红框、文本或禁用按钮，也会在生成步骤前被拦掉。

另有大量需求本身不是网页可见行为：身份/角色矩阵、客户/订单/库存/审批数据、服务端校验、事务、并发、回调、第三方推送和定时任务。现有公开 H5 URL 不提供这些测试所需的 API 契约、sandbox、角色凭据、数据库/日志证据或可回滚数据。不能把页面标题断言伪装成这些测试已经执行。

## 这次修复

- 浏览器执行门禁改为检查实际受限 DSL 步骤和具体前置条件；不再单凭覆盖整个业务流程的 `sideEffectRisk` 标签拦截只读断言。
- 单独识别导入器的泛化前置条件；生成 UI 步骤时忽略这个模板句，但具体账号、历史记录、接口契约、sandbox 和清理条件仍须满足。
- 为可直接观察的 UI 预期重新生成空步骤和仅有通用标题/导航的步骤。生成结果必须包含结果断言，只有页面标题的草稿仍会被拒绝。
- 新增 `assertFieldInvalid`，确定性 lane、Computer Use 服务端复核和 ZIP 中可脱离 AI 运行的脚本都支持红框/无效状态断言。
- 增加断言充分性检查：`case-47` 原步骤只检查“提交按钮禁用”，无法证明“所在地区标红”；现在双通道都会将它标成“现有步骤不足”，不会再误报通过。要触发该错误态需要安全的前端校验触发机制；不会为了它点击可能提交的按钮。
- 未生成步骤的警告按缺失资料分类，并完整列出相应用例 ID，避免只报告模糊的“风险或前置条件未确认”。
- 修订 `.agents/skills/testpilot-qa-workflow/SKILL.md`：要求修复空步骤和泛化步骤，区分工作流业务风险与测试动作风险，并列出具体依赖。

### 仍没有可安全执行的内容
